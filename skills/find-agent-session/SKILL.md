# Поиск сессий

Ищи в следующем порядке, пропуская отсутствующие источники:

1. Codex CLI/ACP.
2. Zed Agent.
3. IntelliJ IDEA AI Assistant.
4. Koda.

Если пользователь явно указал источник, ищи в нём.
В остальных случаях переходи к следующему источнику, пока не найдёшь искомое обсуждение или действие; позднее упоминание файла не подтверждает его создание.
Если пользователь запросил все совпадения, проверь все четыре источника.

Уточняй только недостающие критерии поиска.
Принимай любую комбинацию:

- фрагмент текста;
- опциональный период: день, месяц, диапазон от и до, с опциональными временными рамками;
  - если пользователь его не указал в изначальном запросе — спроси.

## Общие правила поиска

Начинай с наиболее узкого фильтра:

- дата или месяц: перед поиском содержимого сузь выборку по датам, если структура хранилища позволяет;
- текст: в текстовых файлах ищи буквальную строку командой `rg -l -F`; сжатые и структурированные хранилища сначала декодируй по правилам источника.
  - если по буквальной строке совпадений не нашлось — попробуй другие формы и синонимы.

Применяй все заданные фильтры совместно.
Для локальных дат учитывай часовой пояс при выборе файлов и проверяй время внутри записей около границ суток.
Не додумывай недостающие критерии.
Не пересказывай содержимое файлов, если пользователь не запросил их разбор.

### Как уточнять поиск

- Для нескольких независимых признаков пересекай списки файлов, например `comm -12` для отсортированных результатов двух `rg -l -F`.
  Несколько `-e` в одном вызове `rg` означают «любой из вариантов», а не «все признаки».
  После пересечения проверь, относятся ли совпадения к одному обсуждению.
- Если конечного имени файла нет, ищи прежнее имя класса, характерную фразу пользователя, ключ задачи, путь рабочего каталога или хеш коммита.
  Для известного коммита `git show -s --format=fuller <hash>` помогает уточнить дату и полный хеш; различай время автора и коммитера.
- Найденный отчёт или поисковая сессия могут содержать ID и путь исходной сессии.
  Переходи по ним и проверяй первоисточник; известный ID сначала ищи в именах файлов, затем в индексах и содержимом.
- Различай просьбу, план, вызов инструмента и результат выполнения.
  Для поиска совершённого действия нужны соответствующий вызов и его результат; упоминание коммита в `git log` не подтверждает, что его создали в этой сессии.
- Учитывай, что дата создания сессии, последнее изменение и время искомого сообщения различаются.
  Даты каталогов и индексы помогают выбрать кандидатов, но окончательно проверяй время записей.
  Если искомое действие не найдено в каталогах за период, проверь сессии, начатые раньше и продолженные в этом периоде.

### Защита контекста

- До запуска поиска задай ограничения вывода: по умолчанию не более 20 путей или 5 фрагментов по 500 символов за вызов.
  Ограничь также общий объём ответа инструмента; его автоматическое усечение — последний барьер, а не способ просмотра результатов.
- Первый проход возвращает только пути и число кандидатов (`rg -l -F`, SQL с явными полями метаданных).
  Если кандидатов много, сохрани полный список во временный файл и обрабатывай порциями; не загружай его целиком в контекст.
- Не выводи сырые строки JSONL/XML, целые чаты, BLOB или распакованные базы.
  Сначала разбери формат, затем извлеки роль, время, идентификатор и короткое окно текста вокруг совпадения.
  `head`, `rg -m` и лимит строк не защищают от одной строки размером в мегабайты — нужен лимит символов.
- Не запускай широкий `rg -n`, `rg -C` или `cat` по архиву сессий.
  Содержимое читай только из выбранных файлов и записей; перед чтением неизвестной структуры выводи имена полей, типы и размеры, а не значения целиком.
- Расширяй поиск по одному признаку: вариант текста, период или источник.
  После пустого результата не снимай все фильтры сразу.
  При усечении или чрезмерном числе совпадений сузь запрос либо разбей выборку; не повторяй его с увеличенным лимитом вывода.
- Отделяй исходное обсуждение от совпадений в процитированных инструкциях, результатах инструментов и поздних поисковых сессиях.
  Используй такие совпадения как указатели на источник; повторяющиеся копии одного фрагмента не выводи.
- Запрос «все совпадения» требует полной проверки, но не полного дампа: собирай результат порциями, сохраняя непросмотренный остаток.
  Не объявляй поиск завершённым по первой порции или усечённому выводу.

## Codex CLI/ACP

Ищи файлы сессий `.jsonl` в `~/.codex/sessions/`; здесь могут храниться сессии как CLI, так и ACP.
Для даты или месяца сначала ограничь поиск каталогами соответствующих дат.
При отсутствии результата проверь также существующие `~/.cache/JetBrains/IntelliJIdea*/aia/codex/sessions/`.

Совпадения в каталоге доступных скиллов не означают, что скилл применяли.
После поиска путей фильтруй реальные сообщения по роли и типу записи; для поиска запросов пользователя используй `response_item` с `role=user` либо `event_msg` с `type=user_message`, не дублируя один запрос из обоих представлений.
Исключай служебные инструкции и процитированные стенограммы.
По `session_meta` проверяй рабочий каталог и источник: проверочная сессия с чужой стенограммой может совпадать по всем ключевым словам.

Если JSONL не дают ответа, проверь `~/.codex/history.jsonl`: записи запросов могут связать формулировку пользователя, время и ID сессии.
Дополнительные указатели могут быть в `~/.codex/state_*.sqlite` и `~/.codex/thread_history_*.sqlite` — пути роллаутов, названия, рабочие каталоги и сохранённые сообщения.
Открывай базы только для чтения (`mode=ro`), сначала проверь схему: имена версий, таблиц и полей меняются.
Совпадение в индексе — повод открыть исходную сессию, а отсутствие в одном индексе не доказывает отсутствие сессии.

## Zed Agent

Открывай базы SQLite только для чтения: `sqlite3.connect('file:/absolute/path?mode=ro', uri=True)`.

- `~/.local/share/zed/threads/threads.db`, таблица `threads`: поля чата `id`, `summary`, `created_at`, `updated_at`, `data_type`, `data`.
- `~/.local/share/zed/db/0-stable/db.sqlite`, таблица `sidebar_threads`: название, идентификаторы агента и сессии, даты и пути рабочего пространства; используй её для различения встроенного и внешних агентов и поиска связанных сессий Codex.

Перед запросами проверь схему: она может меняться между версиями.
Поле `threads.data` может содержать JSON, сжатый zstd (`data_type=zstd`); перед поиском распакуй его.
Обычный SQL `LIKE` и приведение к тексту не ищут внутри сжатых данных.
Используй Python-пакет `zstandard`, если он доступен; при необходимости — системную `libzstd` через `ctypes`.
Распакованный JSON содержит `title` и `messages` с вариантами сообщений вроде `User` и `Agent`; проверь фактическую структуру, вложенное содержимое и результаты инструментов.
Поле `updated_at` обозначает последнее изменение: старое обсуждение может находиться в чате, изменённом позднее.

## IntelliJ IDEA AI Assistant

Проверь `~/.config/JetBrains/IntelliJIdea*/workspace/*.xml`.
Чаты встроенного AI Assistant могут сохраняться здесь независимо от истории агентов в `aia-task-history`; отсутствие в событиях агента не исключает сохранённого чата.
Разбери XML: компонент `ChatSessionStateTemp` → `option[name=chats]/list/SerializedChat` → `option[name=messages]/list/SerializedChatMessage`.
Читай текст сообщений из `option[name=displayContent]`; XML-парсер декодирует экранированные переносы строк и разметку.
Поле `internalContent` может дублировать текст.
Определяй чат по `uid` и `title/SerializedChatTitle/option[name=text]`.
Поле `modifiedAt` — время изменения чата в миллисекундах Unix, а не время каждого сообщения; не исключай чат только потому, что он изменён после искомого периода.
Сначала получи список подходящих файлов, затем выводи только метаданные найденных чатов и короткие релевантные фрагменты: строки исходного XML могут содержать мегабайты посторонних чатов.

При необходимости проверь также `~/.config/JetBrains/IntelliJIdea*/aia-task-history/`.
Файлы `.agentsession` связывают идентификаторы чатов IDEA с идентификаторами сессий внешних агентов.
Файлы `.events` могут начинаться с `AUI_EVENTS_V1`, после которого идут строки JSON в base64; перед поиском декодируй их.

## Koda

Проверь `~/.koda/sessions/sessions.json` и другие файлы сессий в `~/.koda/sessions/`.
Затем ищи в `~/.kodacli/tmp/*/logs.json` и JSON-файлах журналов сессий в тех же каталогах.
Сначала проверь структуру JSON: `logs.json` может содержать список с полями `sessionId`, `messageId`, `type`, `message` и `timestamp`.
Пустой индекс сессий не исключает сохранившихся журналов в `.kodacli/tmp`.

## Результат

Ограничивай вывод: сначала список подходящих файлов, затем только релевантные сообщения и короткие фрагменты.
Верни абсолютные пути найденных источников, по одному на строку, в порядке приоритета источников; внутри каждого источника отсортируй пути.
Для XML и SQLite с несколькими чатами укажи также название и идентификатор чата.
Если совпадений нет, ответь: «Подходящие файлы сессий не найдены».
