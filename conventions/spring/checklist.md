# Чеклист стиля Spring

## Регистрация компонентов

- Компоненты без зависимостей от других managed beans реализованы как обычные `object`?

## Внедрение зависимостей

- Для управляемых Spring-зависимостей использовано внедрение через конструктор, а внедрение через поля — только если конструктор недоступен или несовместим с жизненным циклом фреймворка либо теста?

## HTTP-клиенты

- Вместо `RestTemplate` предпочтены `RestClient`/`WebClient`, а в HTTP-тестах — `RestTestClient`/`WebTestClient`?
- Для статических путей при использовании `RestClient`, `WebClient`, `RestTestClient` и `WebTestClient` предпочтены простые URI-шаблоны вместо построения URI через `UriBuilder`?

## JDBC

- Для нового или изменяемого SQL-доступа через Spring JDBC использован `JdbcClient`, если контекст проекта не задаёт другое правило?
- Отсутствует переписывание существующего рабочего доступа к данным только ради перехода на `JdbcClient`?
- Для маппинга строк выбран первый подходящий вариант: `JdbcAggregateTemplate.getRowMapper(...)`, затем `DataClassRowMapper`, затем собственный `RowMapper`?

## Kotlin API

- Kotlin-расширения Spring предпочтены эквивалентным Java-перегрузкам с `Class<T>`?
