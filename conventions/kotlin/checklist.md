# Чеклист стиля Kotlin

## Общие правила

- Предпочтены неизменяемые данные, `val`, чистые функции и преобразования через `map`/`filter`, когда они сохраняют ясность кода?
- Нуллабельные типы заменены другими конструкциями языка или дизайном там, где это возможно?
- Поведение без зависимости от состояния класса вынесено в верхнеуровневые функции, а несколько тесно связанных функций — в объект-синглтон?

## Форматирование и идиомы

- В новом коде добавлены пустые строки после заголовка класса и вокруг методов, а пустые строки существующих блоков сохранены?
- Язык комментариев соответствует правилам проекта?
- Использованы синтаксис операторов и доступные перегрузки с материализованными дженериками вместо эквивалентных вызовов `operator fun` и Java-перегрузок с `Class<T>`?
- Тела-выражения представляют только быстрое безопасное поведение: функционально чистое либо ограниченное быстрыми безопасными чтениями глобального окружения?
- При оценке тела-выражения учтена работа, отложенная через лямбды, последовательности, потоки, futures и аналогичные ленивые значения; для другого I/O, изменения наблюдаемого состояния, потенциальной блокировки и владения жизненным циклом ресурсов использованы тела-блоки?
- Для констант и переменных с именем, отличным от имени параметра, использованы именованные аргументы?
- Полные имена в местах использования заменены импортами или алиасами, а способ импорта сохранён, если его изменения не требует пользователь или линтер?

## API

- Значения по умолчанию использованы только для обратной совместимости опубликованного API либо когда больше половины клиентов используют одно значение и его случайный пропуск безопасен?

## Тесты

- В тестах предпочтён `!!` обработке отсутствующего значения, когда требуется присутствующее значение?
- Имена существующих тестовых классов и файлов сохранены, если переименование явно не запрошено?
